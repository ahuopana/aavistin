# 7. Background job backend: django-tasks + django-tasks-db

Status: Accepted

## Context

`docs/architecture.md`'s baseline table and "API, jobs, tooling and operations" section left background jobs as an open question: "Django tasks, Celery with Redis, or a PostgreSQL-backed queue?" — naming LDAP sync, notifications, imports and dashboard precomputation as future job types.

This stopped being purely hypothetical once `apps/assessments/services.py::recompute_staleness()` and `apps/risk/approval.py::recompute_staleness()` shipped in Milestones 5 and 6: both docstrings said automatic recomputation was deferred pending this decision, with a manual management command (`refresh_assessment_staleness`, `refresh_risk_assessment_staleness`) standing in.

Current infra is deliberately minimal (`docker-compose.yml`: `db` and `web` only, no Redis, no worker), and the project's hard rules pin Postgres everywhere and `uv`/`ruff` tooling. ADR-0003 already set a precedent for this project: prefer the smallest, most auditable option that covers the real, current need over a heavier one sized for hypothetical future load.

## Decision

Adopt **`django-tasks` + `django-tasks-db`** (its Postgres-backed `DatabaseBackend`), not Celery+Redis, not Procrastinate.

- **Rejects Celery+Redis.** The real job list today is two cheap, non-latency-sensitive periodic queries. A new stateful service (Redis) plus two new process types (worker, beat) is the wrong-sized tool, and breaks the "Postgres everywhere, one datastore" pattern the architecture doc already commits to for other reasons (full-text search, `ArrayField`).
- **Satisfies both named non-Celery options in the doc at once.** "Django's built-in tasks framework" and "a PostgreSQL-backed queue" read as two options in the doc's phrasing; `django-tasks-db` is literally the first, backed by the second.
- **On a path to obsolescence, in a good way.** `django-tasks` is the pre-core backport of the API Django 6.0 ships as `django.tasks`. The project deliberately pins `django~=5.2` (current LTS); `django-tasks-db` 0.13+ is written to work transparently against either the standalone `django-tasks` package (via `django-tasks-db`'s compat shim, confirmed by reading its `compat.py`) or Django's own core `django.tasks` once present, with the same `@task`/`.enqueue()` API either way. That's a dependency the project can expect to shed later, not one it's stuck with.
- **Rejected alternative: Procrastinate.** More mature than `django-tasks` (0.x), Postgres LISTEN/NOTIFY-based, and ships built-in cron scheduling — which `django-tasks` lacks by design (DEP 14 scopes it to the queue, the same way Celery needs beat separately). Procrastinate loses out because it's a permanent dependency with no path to Django absorbing it upstream, and a heavier API surface for a job list this small. If `django-tasks`'s youth becomes a real problem (churn, abandonment), Procrastinate is the documented fallback.
- **The periodic-scheduling gap is filled with the smallest thing that works**, not a heavier scheduler: `apps/core/management/commands/scheduler.py` is a stdlib-only loop (`time.sleep` + `signal` for clean shutdown) that enqueues due tasks on an interval. It only enqueues; `db_worker` (from `django-tasks-db`) does the actual work, run as a separate process so a slow task never delays the next tick. This matches ADR-0003's preference for small, hand-written, auditable code over a bigger dependency. A single-replica scheduler is fine at this project's current scale — no distributed lock needed yet.

### Integration

- `TASKS` setting (`config/settings.py`) always points at `django_tasks_db.backend.DatabaseBackend` — Postgres-backed in every environment, same as `DATABASES`, no env-var toggle (unlike `LDAP_ENABLED`; this isn't optional infra the way LDAP is).
- Tests force the immediate (synchronous, in-process) backend via an autouse fixture in `conftest.py`, using pytest-django's `settings` fixture — no worker needed to test task logic.
- `docker-compose.yml` gets two new services, `worker` (`manage.py db_worker`) and `scheduler` (`manage.py scheduler`), both built from the same image as `web` with a different command. No Redis, no beat.
- The existing "loop all APPROVED records, recompute" logic moved out of each management command's `handle()` into the service layer itself — `apps/assessments/services.py::recompute_all_staleness()` and `apps/risk/approval.py::recompute_all_staleness()` — so the manual command, the periodic task, and any future caller share one code path. `apps/assessments/tasks.py` and `apps/risk/tasks.py` are thin `@task` wrappers around that shared function; no business logic lives in a task module.
- Recomputation is still never triggered by a signal on every answer/rating edit — only by the manual command or the periodic task — so a single edit doesn't cause a recompute storm across every assessment that might reference it.

## Consequences

- Two new long-running processes in `docker-compose.yml` (`worker`, `scheduler`); no new stateful service (no Redis).
- `apps/*/tasks.py` established as the convention for future background work (a future `apps/accounts/tasks.py::sync_ldap_groups`, `apps/packages/tasks.py::import_package_task`, etc. would follow the same shape) — none of those are built yet; nothing in the codebase demonstrates a concrete need for them beyond the architecture doc's one-line mentions, so they're deliberately not speculative-built here (matches this project's established "services solid, tested; UI/infra minimal until there's a concrete need" pattern visible throughout `apps/packages`, `apps/assessments`, `apps/risk`).
- `django-tasks`/`django-tasks-db` are 0.x and move fast — confirmed directly while integrating this (see below). Pin conservatively and re-read the changelog before bumping.
- Testing the real `DatabaseBackend` + `db_worker` path automatically (not just the immediate backend) turned out to need `TransactionTestCase`, because the worker's own `SELECT ... FOR UPDATE SKIP LOCKED` needs a real, committed transaction that `TestCase`'s per-test wrapping transaction doesn't allow — and even with `serialized_rollback=True`, this interacted badly with pytest's `--reuse-db` (a `TransactionTestCase` flush left the shared test database missing migration-seeded rows, like `apps.products`' `TargetMarket`, for later test runs that reused it). Rather than fight that, the real worker path is verified manually (`manage.py scheduler --once` then `manage.py db_worker --interval 1`, confirming `DBTaskResult` rows reach `SUCCESSFUL`) and automated coverage stays at the "call the task directly under the immediate backend" level, per the original integration plan's own guidance. If this decision is revisited, `pytest-django`'s `django_db` marker with `transaction=True` and explicit fixture teardown may be worth another look, ideally in a dedicated CI job that always recreates the test database rather than reusing it.
- **Correction to the original integration plan while implementing:** the plan assumed `django-tasks-db` always depends on the standalone `django-tasks` package. As of `django-tasks-db` 0.13.0 (installed here), that's only true on Django &lt;6 — the package now expects Django 6's core `django.tasks` when available, and requires `django-tasks` to be installed explicitly otherwise (there is no `[compat]` extra on `django-tasks` itself, despite `django-tasks-db`'s own extra of that name suggesting one). Resolved by adding `django-tasks` as a direct dependency alongside `django-tasks-db`. This is exactly the "young, moves fast" risk named above, encountered on first install rather than hypothetically.
