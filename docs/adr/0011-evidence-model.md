# 11. Evidence model: dedup, generic linking, and staleness wiring

Status: Accepted

## Context

`docs/architecture.md`'s "Evidence" section (added alongside this ADR) designs the milestone: a product-scoped `Evidence` record, reused across whatever it satisfies, backed by content-addressed file storage so the same document isn't stored twice. This ADR records the implementation decisions the design left open, and what's deliberately deferred.

## Decisions

- **`last_audited_by` is a `User` FK, not free text.** Every write in this app already goes through a logged-in session (`Assessment.approved_by`, `EvidenceFile.uploaded_by`, and every `HistoricalRecords` entry are all `request.user`); there's no path for an external actor to touch an `Evidence` row directly. Recording *who performed an audit outside the system* (e.g. a named external certification body) was considered and explicitly deferred — not needed yet.
- **Delete protection is a precise frozen-snapshot scan.** `apps.evidence.services._referenced_by_approved_work` blocks deleting `Evidence` only if its id actually appears inside an approved (frozen) `RiskAssessment` or `Assessment` snapshot — a live `EvidenceLink` that was added after approval, or never approved at all, doesn't block deletion, since nothing approved actually depends on it yet. Both `apps.risk.approval`'s and `apps.assessments.evaluation`'s evidence fingerprints embed `evidence_id`, so the check is a straightforward scan of each approved snapshot for the product, not a JSON query.
- **Staleness is wired into both `apps.risk` and `apps.assessments`.** `apps.risk.approval.build_snapshot()` already marks a `RiskAssessment` stale by rebuilding the current view and diffing it against the frozen one (no separate "trigger" list) — extending it to also fingerprint each `Control`'s currently-linked evidence (which ids, and whether each is still current: not expired, not superseded) was a small, natural addition, read through `Control`'s reverse `evidence_links` relation so `apps.risk` never has to import `apps.evidence`. `apps.assessments.evaluate_configuration` embeds the same shape of fingerprint into each result's new `requirement_evidence` key, for every requirement a package's content declares that has at least one linked `EvidenceLink`; `apps.assessments.services.recompute_staleness` diffs a `(source, version) -> requirement_evidence` summary between the current evaluation and the frozen snapshot, alongside its existing `resolved_answers`/package-version checks. Unlike `apps.risk`, `apps.assessments.evaluation` does import `apps.evidence.models` directly (`EvidenceLink` has no natural reverse relation to hang off, since a requirement is a string id, not a row) — this is a one-directional dependency (`apps.evidence.models` never imports `apps.assessments`), so no import cycle.
- **No UI in this milestone.** `apps.risk` shipped its own models/services/staleness (milestone 6) before any UI followed in a later pass; `apps.evidence` follows the same shape — models, services (dedup, linking, delete protection), admin, and tests are complete and tested; views/templates for attaching evidence through the product-facing app (rather than Django admin) are left for a follow-up, consistent with how risk-register UI was also deferred past its own initial milestone.
- **`EvidenceLink` is one model with a `target_type` discriminator**, not two separate models or a `ContentType`-based generic FK. `Control` is a real row (FK-able); a requirement is a string id inside a versioned `RequirementPackage`'s JSON content, never a database row (`docs/architecture.md`, "Requirement sources" — app code must not hard-code regulation structure). Since the two target shapes are genuinely different, a single `GenericForeignKey` wouldn't fit either cleanly; the conditional-fields-by-type shape already used by `apps.risk.HazardCause` fit both without inventing a new pattern.
- **File storage is content-addressed by SHA-256, not per-`Evidence` paths.** `EvidenceFile` is global, not product-scoped — the same document reused as evidence in two products is stored once and referenced by two `Evidence` rows. `apps.evidence.services.store_evidence_file` checks for an existing checksum before writing; a race between two uploads of identical content is resolved via the checksum's unique constraint (retry-on-conflict), not a lock. `apps.evidence.services.delete_evidence` only removes the stored blob once no `Evidence` row references it any more.

## Consequences

- A follow-up PR is still needed for product-facing UI (list/attach/upload views, following `apps/products/views.py`'s established shape) — the only piece of this milestone left unbuilt.
- `MEDIA_URL`/`MEDIA_ROOT` are new to this project (`config/settings.py`); `media/` was already gitignored, anticipating this. Served via Django's dev-only static helper in `config/urls.py` when `DEBUG=True`; production media serving (e.g. a reverse proxy or object storage) is out of scope here.
- `apps.risk.approval.build_snapshot()` now includes a `"controls"` key even for configurations with no controls (an empty list); `apps.assessments.evaluate_configuration`'s per-result dicts now include a `"requirement_evidence"` key. Existing callers of either are unaffected — no existing test asserted exact snapshot/result equality.
